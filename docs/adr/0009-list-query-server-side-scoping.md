# ADR-0009: 一覧の絞り込み・並び替え・ページングをサーバー側で行い、URLクエリを唯一の状態源とする

- **ステータス**: Proposed
- **日付**: 2026-09-10
- **決定者**: @Natsugure
- **関連**: [ADR-0001](./0001-layer-structure.md), [ADR-0002](./0002-dependency-inversion-ports.md), [ADR-0003](./0003-read-write-separation.md), GitHub Issue #94

---

## コンテキストと課題

### 問題1: ADR-0003 が保留した論点である

[ADR-0003](./0003-read-write-separation.md) は Repository で統一する案（選択肢1）を
却下した理由として、次を挙げた。

> ページネーション・ソート・部分選択を渡そうとすると interface に Drizzle の概念が
> 滲み出し、抽象化が漏れる

Query Service を採用したことでこの漏れそのものは避けられたが、
**一覧の絞り込み条件を port にどう渡すか**は決めていなかった。
Issue #94（駅・路線一覧の事業者スコープ化・検索・並び替え）が、admin で初めて
この種の port を必要とする。

### 問題2: スコープ無しでは成立しない規模である

実測（2026-09-10, Neon `development`）: 事業者162 / 路線602 / 駅10,625。
最大の事業者（JR東日本）だけで86路線・1,961駅を持つ。
`stations.operator_id` / `station_lines.line_id` に索引は無い
（[docs/domain/station-visibility.md](../domain/station-visibility.md) の
「この規模では専用索引を置かない」方針）。

`apps/admin/src/app/stations/page.tsx` は改修前、この10,625行を無条件に1本の
JOIN で読み、JS で3階層（事業者→路線→駅）に畳んで全描画していた。
LIMIT もスコープも無い。

### 問題3: 状態の置き場が決まっていない

スコープ・検索語・ソート・ページを `useState` に置くと、リロード・共有・
戻る操作で失われる。admin には既に `?operatorId=&lineId=` を `router.push` で
更新する先例がある（`stations/[stationId]/connections/new`、#49 / #88）が、
一覧に適用した例は無かった。

## 検討した選択肢

| | 内容 | 1,961駅のとき | URL復元 | 新規依存 |
|---|---|---|---|---|
| **1** | クライアント全読み + 仮想スクロール | RSCペイロードに全行が載る | 自前実装が要る | 仮想スクロールライブラリ |
| **2** | `@tanstack/react-table` / `mantine-datatable` | 同上 | 自前実装が要る | あり |
| **3** | サーバー側で `WHERE` / `ORDER BY` / `LIMIT OFFSET` | LIMIT件のみ | 自然に得られる | なし |
| **4** | カーソルページング | LIMIT件のみ | 自然に得られる | なし |

## 決定

**選択肢3を採用する。**

一覧の scope（事業者・路線などの絞り込み対象）・検索語・並び替え・ページングは
すべて SQL 側（`WHERE` / `ORDER BY` / `LIMIT OFFSET`）で処理し、
**URL クエリを唯一の状態源とする。** 一覧コンポーネントに、これらを表す
`useState` を持たせない。

port にソートキーを渡すときは、**画面ごとの文字列 union**（例:
`'line' | 'code' | 'name' | 'published'`）で表す。`SQL` 式・カラム参照・
`asc()`/`desc()` を port に持ち込まない。union から Drizzle の式への変換は
`external/query/*.ts` の実装内だけで行う。これが問題1（ADR-0003 が保留した
漏れ）への回答である。

**共通化するのは「引数と戻り値の形」だけであり、クエリ本体は共通化しない。**
ADR-0003 の以下の決定はそのまま維持する。

> 同じテーブルを引く Query Service が複数存在する（略）。
> 共通化しないこと自体が決定事項である。

したがって、テーブルを引数に取る汎用の `listQuery(table, params)` のような
ヘルパは作らない。各一覧（駅一覧・路線一覧など）は、それぞれ独立した
Query Service 実装を持つ。

具体的な型定義（`ListParams` / `ListResult` 等）とソートキーの一覧は、
実装のたびに変わりうる詳細であるため本 ADR には書かない。
[docs/spec/design.md](../spec/design.md) を参照する
（[ADR README](./README.md)「具体的な型定義・シグネチャは書かない」）。

### スコープ・検索語が無いときはクエリを発行しない

スコープにも検索語にも該当が無いとき、一覧本体と件数のクエリを発行しない。
選択肢の供給に必要な最小限（例: 事業者セレクトの162件）だけを読む。

## 各選択肢の評価

**選択肢1・2の悪い点**: RSC のペイロードに最大1,961行が載る。
「表示中のページ内だけ絞り込む」という、実態と異なる挙動になる
（本当は全件を読んでいるのに、あたかもサーバー側で絞ったかのように見える）。
一覧画面は駅・路線の2つのみであり、そのためだけに `@tanstack/react-table` や
`mantine-datatable` を導入する理由に乏しい。

**選択肢4の悪い点**: 総件数を出せず、任意ページへ飛べない。
10,625行規模での OFFSET ページングは実測上問題にならない
（Postgres の `count(*)` と `LIMIT/OFFSET` はこの行数では実用速度に収まる）。

## 結果

### 肯定的な結果

- 一覧クエリを足す作業が「`ListParams` を受ける Query Service を1本足す」に
  定式化され、#48（API GET の Query Service 化）や他の一覧（列車・事業者）が
  同じ形に揃えられる
- リロード・共有・戻る操作で一覧の状態が復元される
- port が Drizzle に依存しないため、ADR-0002 が要求するテスタビリティ
  （Fake を注入した usecase テスト）を損なわない

### 否定的な結果・受け入れるトレードオフ

- 検索語の入力ごとに（デバウンス後）RSC ラウンドトリップが発生する
- 一覧クエリのたびに `count(*)` が1本増える
- OFFSET ページングは深いページで線形に劣化する。この規模では許容し、
  劣化が実測で観測された時点で選択肢4（カーソルページング）への移行を検討する
  （下記「見直し条件」）

### 適用範囲

Issue #94 の対象である admin の `/stations` `/lines` に適用する。
`/trains` `/operators` は件数が小さく（列車・事業者とも数百件未満）、
本 ADR の対象外とする（移行する場合は別 Issue）。

### 見直し条件

- 1テーブルが10万行規模になり、OFFSET または `count(*)` の劣化が実測で
  観測されたとき（→ カーソルページングへの移行を検討する）
- 画面ごとのソートキー union が実質同一のまま5画面を超えたとき
  （＝ADR-0003 の見直し条件「Query Service を薄い共通ヘルパに寄せる余地」に
  接続する）
